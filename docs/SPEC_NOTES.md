# 仕様書（Deck級ベンチマーク 仕様書）との対応

仕様書の各節が、どこでどう実装されているか。仕様どおりにできなかった所・解釈が必要だった所は **判断** として理由を書く。
数値は Linux 版をソフトウェア Vulkan（lavapipe）で描いたときの `render_stats`（CPU 側の可視判定による推定）。

## 目的とスコープ

| 仕様 | 実装 |
| --- | --- |
| Android 11（API 30）以上、Vulkan 1.1 以上（未満はインストール不可） | `minSdk 30`、マニフェストの `uses-feature android.hardware.vulkan.version 0x401000 required`。起動時にも `hasSystemFeature` で確認 |
| 兄弟ビルド（Linux/Vulkan で Deck 実機の基準取り） | `linux/`（SDL2）。描画・計測コードは `core/` を APK と共有 |
| 成果物：APK（arm64-v8a）、Linux版、60秒のシーン1本、スコア、フレームタイム統計、JSON/CSV | すべてあり。CSV の列は仕様どおり |
| 非対象：レイトレ、実ゲームのアセット・名称・ロゴ | レイトレなし。街・人・車・看板は手続き生成、看板は文字でない幾何模様、アプリ名は仮称 BenchDeck |
| Filament を採用（Godot は不採用） | Filament v1.77.1 |

## 基準値・プリセット

- Deck プリセットの値は仕様の「再現対象とする設定」表どおり（`scenes/scene_v1.json` の `presets.deck`、単体テスト `Config.DeckPresetMatchesSpec` で固定）。
- Low / Medium / High も仕様の4段表どおり。
- 基準値 `baseline` は **未設定（null）**。Steam Deck 実機でのキャリブレーション後に `--write-baseline` で書き込む（README）。未設定の間はスコアを出さず fps のみ。

### 判断：仕様書内の数値の食い違い

仕様書の「シーン設計」表（初期負荷目安）と「プリセット」表・シーン定義JSONで値が違う箇所は、**プリセット表・JSON を正**とした。
シーン定義 JSON が「負荷のノブは全部ここ」という仕様上の唯一の出所で、プリセット表が Cyberpunk の Deck 設定に対応づけられているため。

| 項目 | シーン設計表 | 採用した値 |
| --- | --- | --- |
| SSR | 1/2解像度・16ステップ（Low相当） | 1/2解像度・24ステップ（Deck=Medium） |
| フォグ | 80×50×64 | 120×75×64 |
| 動的光源 | 256灯 | 296灯（ネオン点200＋ネオンスポット56＋街灯40）。ただし下記の255灯制限あり |
| 群衆 | 60体（Low相当） | 60体（crowd_scale 1.0、Medium扱い） |

### 判断：人・車の素材（Quaternius / Kenney）→ 手続き生成

Quaternius の配布は itch.io のブラウザ操作が必要で、スクリプトから取得できない（仕様の「手作業を残さない」に反する）。
そのため人・車もコードで生成した。仕様の予算（人 平均13k tri・リグ付き・色違い4種、車 3車種 各5k tri以下）は満たし、
単体テスト（`Procgen.CharacterBudget`, `Procgen.VehicleBudget`）で固定している。

### 判断：ボリューメトリックフォグの作り方

Filament のグローバルフォグにはライト散乱がない（仕様どおり）。ただしスクリーン空間のレイマーチには深度バッファを
読むポストプロセスが必要で、Filament は公開 API で任意のポストプロセスを差し込めない。そこで **視錐台スライス方式**にした：
`grid[2]` 枚のスライスを奥から描き、各スライスを `grid[0]×grid[1]` の格子で張る。格子点＝フロクセルで、
頂点シェーダが密度（高さ減衰＋流れるノイズ）と、近い 16 灯＋月光の散乱（HG 位相関数）を計算し、画素は補間するだけ。
スライスの奥行きは毎フレームずらし、TAA で縞を消す。格子の読み方は仕様の「フォグ解像度 = レイマーチの解像度×ステップ数」と同じ。

### 判断：パーティクルの「コンピュート更新」

Filament にはコンピュートシェーダの公開 API がない。雨・蒸気は **頂点属性なし描画**で、粒子の位置を時刻とハッシュだけから
頂点シェーダで決める（状態を持たない GPU 更新）。CPU 負荷ゼロで、描画・オーバードローの負荷は同じ。どの端末でも同じ絵になる。

### 判断：SSR の「1/2解像度・24ステップ」

Filament の SSR には解像度・ステップ数の設定がない（`thickness / bias / maxDistance / stride` のみ）。
マーチの回数は最大距離÷刻みに比例するので、**刻み 2（1/2解像度相当）、最大距離 = 4 + 0.5×steps [m]** に対応づけた。

### 判断：光源の 255 灯制限

Filament は 1 ビューで最大 255 灯（`CONFIG_MAX_LIGHT_COUNT`）で、超えた分は黙って捨てる。捨てられる灯が端末や
フレームで変わると比較できないので、**カメラに近い順に 250 灯だけをシーンに入れる**（＋月）。総数 296 灯は仕様どおり。

## 画面とフロー・ライフサイクル

仕様の状態遷移（起動チェック → ホーム → 冷却待ち → 読込 → ウォームアップ → 計測 → 結果 / 中断）と、
事象ごとの処理表（Vulkan なし、Engine 作成失敗、onPause / surfaceDestroyed、onResume、回転・折りたたみ、
onTrimMemory、サーマル SEVERE、アセット読込失敗、通知・着信）はすべて実装した。
計測中の表示は右上の区間名と fps（1秒に1回更新）。

## 計測方法とスコア

| 仕様 | 実装 |
| --- | --- |
| 冷却待ち：`getThermalHeadroom()` が 0.5 未満になるまで | **変更**。ヘッドルームの 0.0 は「1.0（SEVERE）から一定の距離」で室温ではないため（AOSP `PowerManager#getThermalHeadroom` の説明）、端末によっては放置しても 0.5 を下回らず永遠に始まらない。`CoolingPolicy` で「LIGHT のしきい値 − 0.05 未満（Android 15+ でしきい値がある端末）／しきい値が無ければ 0.5 未満か、60 秒の低下が 0.02 未満（下がり止まり）」で開始、MODERATE 以上は待つ、最大 10 分、手動スキップ可。取得は 10 秒ごと（ADPF の推奨間隔）。開始理由は結果 JSON の `cooling` |
| ウォームアップ：全バリアント事前生成＋1周（計測外） | 読込中に3地点を描いてシェーダを作らせたうえで、1周を計測外で走らせる |
| 本計測3周、GPU時間 = `gpuFrameDuration`、CPU時間 = FrameInfo の beginFrame〜endFrame、表示間隔 = Choreographer、サーマル | そのとおり。結果 JSON の `frames` に全フレーム |
| スコアは GPU 時間と CPU 時間の大きい方から | そのとおり |
| MODERATE 以上の周回は無効 | そのとおり（`invalid_reason: thermal_moderate` など） |
| 集計：平均、1% low、0.1% low、中央値、p99、区間別 | そのとおり |

### 判断：フレームの送り方

Filament は「1つ前のフレームの GPU 処理が終わっていないと `beginFrame` がフレームを捨てる」。表示同期を待たない
計測ループでは空回りして CPU を燃やし（スマホでは発熱が増える）、GPU 時間のクエリも取りこぼす。
そこで `beginFrame` の直前に前フレームのフェンスを待つ。次フレームのシーン更新は前フレームの GPU 処理と並行する。
GPU 時間が取れたフレームの割合を `gpu_coverage` として記録し、半分未満なら `timing_method` を CPU＋表示間隔に切り替えて明記する。

## テスト計画・配布

README の表のとおり。タグ `v*`（または Actions から版を指定して手動実行）で テスト → ビルド → 署名 → Release
（SHA-256、リリースノートにシーン定義の版・スコア互換性・基準値・既知の問題）まで自動。
エミュレータ試験はリリースを止めない（起動確認は実機で行う方針）。署名鍵の Secrets が無い間は debug 鍵で署名した
リリースビルドをプレリリースとして出す。

### 描画一致（仕様：Linux 版と APK の固定カメラ 5 点、PSNR 40dB 以上）→ **基準を変更**

測定（shot_0、1280×800、CC0 素材なし）：

| 比べたもの | 等倍 PSNR |
| --- | --- |
| Linux 版 lavapipe（手元）vs Linux 版 lavapipe（CI） | 63.3 dB |
| **同じ Linux 版**を lavapipe と SwiftShader で | **25.6 dB** |
| SwiftShader（Chromium 同梱）vs SwiftShader（Android Emulator 同梱） | 約 50 dB |
| Linux 版（Emulator 同梱 SwiftShader）vs APK（16KB エミュレータ） | 31.2〜35.7 dB（5 点） |

同じプログラムでも Vulkan 実装が違うだけで 25dB 台になる（雨粒・TAA のジッタ・ディザ・ハッシュのセル境界など、
1 画素単位で揺れる要素が多いシーンのため）。等倍 40dB は同じ GPU 実装どうしでしか成り立たない。そこで：

- 基準画像はエミュレータと**同じ SwiftShader**（Android Emulator 同梱）で Linux 版を描く
- 判定は **1/4 縮小（平均）の PSNR 29dB 以上**かつ**チャンネル平均差 5.5 以下**（`tools/imagediff.py`）
- 感度の確認（shot_0 に人工的な不具合を入れて比べた）：物体 1 つ欠け（200×200）25.8dB、画面上部 40% が暗い 27.4dB、
  別の時刻のショット 17.3dB、露出 +15% は平均差 6.0 でいずれも不合格。赤 +10% は検出できない（平均差 4.0）

**未解明**：同じ SwiftShader でも APK の方が中間調で約 8% 明るく（平均差 最大 3.7）、差は濡れた路面の反射に集中する。
エミュレータの GPU 転送層（gfxstream）か Android 側の経路の違いと考えているが、この環境ではエミュレータを動かせず
（KVM なし）特定できていない。実機では GPU ごとに描画が違って当然なので、実機ではこの試験を合否ではなく目視の参考にする。
